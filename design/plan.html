Quantum Optics Digest

A morning page of new arXiv papers on superconducting artificial atoms and quantum optics, ranked by a Claude Code cloud routine and published on GitHub Pages. This document records what was decided, why, and the order in which to build it.

Summary

Every weekday at 09:00 Moscow time a cloud routine clones the repo, runs a Python script that pulls the last seven days of arXiv listings for three fixed query sets, drops anything already shown, enriches the rest with Semantic Scholar metadata, and hands the candidates to the routine's own model. The model sorts them into three sections, scores each against a written statement of your interests, writes a one-line reason per paper, and commits a JSON digest. A render script turns the digest into a static page and the commit lands on GitHub Pages. Saturday at 10:00 a second routine does the same for the week's superconducting quantum computing papers, using a stronger model.

No MCP server is involved in the routine. The arxiv and Semantic Scholar MCP servers you installed are thin wrappers over the same public APIs and cannot be attached to a cloud routine. They will be registered in Claude Code for your interactive sessions only.

Constraints found

Cloud routines cannot attach local MCP servers. Routines run in Anthropic's cloud and accept only claude.ai connectors over HTTP. Your arxiv and Semantic Scholar servers are stdio processes installed with uv on this Mac. They are registered today only in Codex, not in Claude Code.

Routines have no persistent disk. Anything that must survive between runs lives in the git repo and is committed.

The routine's network is an allowlist. The Default environment reaches package registries and GitHub only. export.arxiv.org must be added under Custom network access with the default list kept. api.semanticscholar.org is reached by storing the key as an environment API credential, which both attaches the key outside the sandbox and opens the host. Python, uv, and gh are preinstalled on the Ubuntu VM.

Pushes to main are conditional. A routine may push to a branch other than claude/* only if that branch is unprotected, nobody else has an open pull request from it, and every commit on it is yours. Routine commits carry your GitHub identity, so a solo unprotected main satisfies this permanently.

Semantic Scholar terms you accepted. One request per second on all endpoints. Exponential backoff on 429 responses. A key unused for about 60 days may be revoked. The weekday schedule uses the key at least five times a week, so revocation is not a concern while the routine runs.

arXiv API. Around three seconds between requests, occasional 503 responses, and new papers announced Sunday to Thursday around 20:00 US Eastern. Saturday and Sunday mornings in Moscow have no new listings, which is why the daily routine runs weekdays only.

GitHub Pages on a free account requires a public repo. Your query sets and interest statements will be visible to anyone with the URL.

Your machine is a MacBook Air. A local scheduler would run only while the lid is open, which is why the cloud routine won.

Architecture

Deterministic work stays in Python so it is cheap, testable, and reproducible. The model touches only the step that needs judgment. State crosses the boundary as JSON files.

Components

  • fetch.py runs one arXiv query per section over the last seven days sorted by submission date, drops IDs present in the seen file, tags each survivor with keyword flags such as computing or platform:sc, sends the remaining arXiv IDs to Semantic Scholar in one batch call, and writes out/candidates.json plus out/status.json. It updates the seen file only after a successful write so a crash never marks papers as shown.
  • The routine model reads the candidates and the three interest statements, and writes out/ranking.json following the contract below. It never fetches anything itself.
  • render.py merges candidates and ranking into digests/YYYY-MM-DD.json, then regenerates docs/index.html from the last 15 digest files and one archive page per older day. It reads out/status.json and prints the banner when any step reported an error or when the newest digest is older than expected.
  • Scripts declare dependencies inline with PEP 723 metadata and run through uv run, matching how Python is managed on your machine. Expected dependencies: httpx and feedparser. Nothing else.

Queries

arXiv search syntax, fetched with sortBy=submittedDate, max_results=200, and a client-side date filter for the last seven days. Queries are kept broad on purpose. Exclusion is the model's job, guided by the interest statements, because an ANDNOT on "error correction" would drop an optics paper that mentions it in passing.

The pool for section A is split by the model: optics papers go to A, computing papers are tagged computing and held for Saturday. Section B candidates that also match the A query are removed before ranking so a paper appears once.

The weekly run adds one Semantic Scholar bulk search: query "superconducting qubit" | transmon | fluxonium, publication date within the last 14 days, fields of study Physics, limited to papers without an arXiv ID, so only journal-first publications enter.

Interest statements

Drafted from your bullets. These are the files you edit when the digest drifts. The model receives them verbatim.

A. Superconducting artificial atoms, what counts as relevant

Quantum optics with superconducting circuits. Relevant: single-photon and
few-photon sources in the microwave domain; photon correlation measurements
(g2, cross-correlation, antibunching); temporal and spectral shaping of
itinerant microwave photons; quantum state transfer between qubits, cavities
or nodes; quantum information protocols carried out on a few qubits where
the physics, not the benchmark, is the point; time-domain and time-bin
entangled states; waveguide QED, giant atoms, dressed states, scattering off
one or a few artificial atoms. Not relevant for the daily digest: error
correction, surface codes, multi-qubit processors, gate fidelity records,
fabrication-only papers, and calibration tooling. Tag those "computing"
and give them a low daily score.

B. Other platforms, what is already standard

Well known and to be scored low unless there is a genuinely new twist:
transmission and reflection measurements of a single emitter coupled to an
open transmission line or open waveguide, including the usual extinction,
Mollow triplet and power-broadening results. Score high: experiments or
theory that show an effect, regime or protocol not obvious from the
standard cavity or waveguide QED toolbox, on any platform (atoms, ions,
quantum dots, colour centres, optomechanics, photonic circuits).

C. Dark matter with superconducting devices

Proposals and results that use superconducting qubits, resonators, single
microwave photon detectors or quantum sensing protocols to search for axions,
dark photons or other dark matter candidates. Include instrumentation papers
if the detector is qubit or photon-counting based. Exclude pure astrophysics.

Weekly. Superconducting quantum computing, what is hot

From the week's computing-tagged papers pick ten that a researcher in
superconducting qubits would want to have heard of: new records, new qubit
designs or couplers, new architectures, error-correction milestones,
results from major groups, and anything already collecting citations.
Prefer results over surveys.

Ranking contract

The routine prompt asks the model to read out/candidates.json and write out/ranking.json. The shape is fixed so render.py never has to interpret prose.

// out/candidates.json  (written by fetch.py)
[{ "id": "2609.01234", "title": "...", "authors": ["..."], "abstract": "...",
   "categories": ["quant-ph"], "submitted": "2026-09-13", "pool": "A",
   "tags": ["platform:sc", "computing"],
   "s2": { "citationCount": 0, "tldr": "...", "venue": "" } }]

// out/ranking.json  (written by the model)
{ "run": "2026-09-14", "mode": "daily",
  "items": [{ "id": "2609.01234", "section": "A", "score": 82,
              "why": "First g2 measurement of a shaped microwave photon from a fluxonium." }] }
  • Score is 0 to 100 against the section's statement. The rubric is written into the prompt: 80 and above means "read today", 50 to 79 "worth the title", below 50 "matched the query but not the interest".
  • Section is one of A, B, C, or computing. A candidate from the A pool that the model tags computing is held for Saturday and not shown daily.
  • Why is at most 25 words, present tense, names the concrete result, never restates the title.
  • Caps. At most 120 candidates per run are sent to the model. If fetch.py finds more, it keeps the newest 120 and reports the overflow in status. Around 60 abstracts of 250 tokens each is roughly 15k input tokens, so cost is not a factor.
  • Rendering rule. Top 10 per section by score, shown with the why line. Everything else in that section goes to a titles-only list. Nothing is dropped, so the query tuning stays visible.

The page

One static page. Dates in Moscow time. No JavaScript needed except a details toggle for the titles-only lists, which works without it.

  • Banner. Shown only when status.json has an error or when the newest digest is more than one working day old. Carries the failing step and the error text, and a link to the routine's run log.
  • Today. Three sections A, B, C. Each entry: title linked to the abstract page, first three authors, submission date, the why line, and the Semantic Scholar citation count and venue when present. A collapsed "also matched" list below each section.
  • This week section, refreshed Saturdays, with the weekly ten and their citation counts.
  • Previous days, the last 14, each collapsed by default with a count of shown papers.
  • Archive link list at the foot, one page per older day, generated from the digest files.

Routines

Two routines in the Default environment. The prompt is kept in the repo as ROUTINE.md so it is versioned, and the routine's message is only "read ROUTINE.md and follow it for mode daily". Both routines get the tools Bash, Read, Write, Edit, Glob, and Grep, and nothing else.

RoutineCron (UTC)ModelSteps in ROUTINE.md
Daily digest0 6 * * 1-5Sonnet 51. uv run scripts/fetch.py --mode daily. 2. Read candidates and interests, write ranking.json. 3. uv run scripts/render.py. 4. Commit digests, state, docs. Push. 5. If any step failed, still run render with --error "text" and commit so the banner shows.
Weekly computing0 7 * * 6Opus 5Same steps with --mode weekly, which loads the week's computing-tagged digests plus the Semantic Scholar venue search.

The Semantic Scholar key is stored as an API credential on the Default environment: host api.semanticscholar.org, header name x-api-key, no prefix. Anthropic's proxy adds the header after the request leaves the VM, so the key never appears in the repo, the session, or any environment variable. fetch.py sends no key itself. If the credential is absent it notes "unauthenticated" in status and the digest still appears.

Rate limits and failure handling

  • Semantic Scholar. A single client in s2.py enforces at most one request per second, retries 429 and 5xx with exponential backoff starting at two seconds and capped at five attempts, and caches every answer in state/s2_cache.json so a paper is never requested twice. Daily traffic is one batch call for up to 100 IDs. Weekly traffic adds one or two bulk searches.
  • arXiv. Three seconds between requests, three sections plus pagination gives under ten requests a run. 503 responses are retried after ten seconds, three times.
  • Missed run. The seven-day window means a failed Tuesday is absorbed by Wednesday's run. Nothing needs manual replay.
  • Partial failure. If Semantic Scholar fails, the digest is produced without enrichment and the banner says so. If arXiv fails for one section, the other two sections still render.
  • Bad model output. render.py validates ranking.json against the contract. On a violation it renders the raw candidate list unranked and shows the banner, so you always get something.

Risks and later work

Risks

  • Cloud egress. Reaching arXiv depends on the Custom allowlist entry, and Semantic Scholar on the API credential. Both are verified in phase 0 before anything is built on them. If either proves unreliable, the fallback is a launchd job running the same scripts locally with claude -p and the page published as a Claude artifact.
  • Git push from the routine. Depends on the GitHub connection granted in phase 0. A failed push leaves the run log as the only record, and the next run redoes the work because seen.json was never committed.
  • Day-to-day ranking variance. The same paper can score differently on different days. The rubric in the prompt and fixed statements reduce this. Version 2 can pin scores per paper in the digest file so a paper never moves after first display.
  • Public reading list. The repo shows your query sets, statements, and what you read. Switch to a private repo and read rendered Markdown on github.com if that becomes uncomfortable.
  • Query drift. arXiv phrasing changes over time. The titles-only list exists so misses inside the pool are visible. Misses outside the pool are not, so revisit queries.toml quarterly.

Version 2 candidates, in rough order of value

  1. Feedback buttons on the page that write to a small shared store and feed the next ranking prompt.
  2. Author watchlist section: any paper by a named list of groups, regardless of query match.
  3. Export of "read today" papers to Zotero through the zotero MCP server in a local session.
  4. Telegram or email push of the top three, if opening the page proves to be the step that gets skipped.
